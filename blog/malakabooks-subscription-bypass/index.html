Subscription Bypass in MalakaBooks: Zero Validation Edition

How a completely unprotected API endpoint let me access premium book subscriptions without paying a single rupiah.

API Vulnerability Broken Authorization Payment Bypass

What is MalakaBooks?

MalakaBooks.id is an Indonesian digital book platform that offers a subscription-based model for premium content. Users can access thousands of books and documents, ranging from fiction to educational material, by paying for monthly or annual subscription plans. It's a pretty standard SaaS model — you sign up, browse content, and if you want to read premium books, you subscribe.

The platform offers three subscription tiers:

  • 3 Month Plan: IDR 80,000 (~$5)
  • 6 Month Plan: IDR 140,000 (~$9)
  • 12 Month Plan: IDR 240,000 (~$15)

All straightforward. Or so it should be.

The Discovery

I was poking around MalakaBooks' API after signing up for an account. Like most modern platforms, the subscription logic lives in REST endpoints. I found a particularly interesting one: POST /subscriptions/mock-activate.

The endpoint name itself is suspicious — why would a production API have "mock" in the endpoint name? Turns out, this wasn't just a naming quirk. It was a completely unprotected subscription activation endpoint that required absolutely zero payment verification.

How the Vulnerability Works

Step 1: Create an account and verify it.

Nothing special — just the standard registration flow on malakabooks.id. Once verified, your account has the reader role, which is the default for free users.

Step 2: Identify a premium book you can't access.

Navigate to any book that requires a subscription. The UI will show a popup with subscription options and a button to start your subscription. If you check your account status via the API endpoint GET /subscriptions/my-status, you'll see "canAccessSubscriptionBooks": false. This confirms you don't have access yet.

Step 3: Bypass the payment entirely.

Here's where it gets interesting. Instead of actually subscribing (which requires payment through a payment gateway), I sent a direct POST request to the `/subscriptions/mock-activate` endpoint:

curl -X POST https://api.malakabooks.id/subscriptions/mock-activate \
-H "Authorization: Bearer YOUR_TOKEN" \
-H "Content-Type: application/json" \
-d '{"planId":"b10a3d56-c1b1-4ba3-a5f0-0f9b6f7c85e0"}'

Response? "message": "Subscription activated successfully".

Step 4: Verify the bypass worked.

Check your status again via GET /subscriptions/my-status. Now your response shows "canAccessSubscriptionBooks": true. The frontend doesn't even need a refresh — the permission changed server-side instantaneously.

Step 5: Access premium content for free.

Go back to any premium book on the website. Instead of a paywall popup, you now see "Start Reading" and "Save to Library" buttons. Full access. No payment. No transaction log. Nothing.

Root Cause: Zero Authorization Checks

The vulnerability boils down to three catastrophic failures:

1. No payment verification. The endpoint doesn't check if you've actually completed a payment transaction. It just accepts a planId and activates the subscription.

2. No rate limiting or role checks. Any authenticated user with the reader role can hit this endpoint. There's no check for administrative privileges or special permissions. If you're logged in, you can activate any subscription plan.

3. Missing transaction validation. The endpoint should validate against the payment gateway (Midtrans, Stripe, whatever they use) to confirm a transaction was completed. It does neither — the endpoint is essentially a direct write to the subscription database with zero guards.

The "/subscriptions/mock-activate" naming suggests this was a testing endpoint that accidentally got left in production. That's not uncommon — I've seen this pattern before in poorly maintained APIs where test endpoints make it to prod and don't get cleaned up or properly restricted.

The Impact

This isn't a theoretical vulnerability. It has real consequences:

  • Direct revenue loss: Every subscription that could be bypassed represents lost revenue. Scale this — write a script to auto-register accounts and activate subscriptions, and you're looking at potentially thousands of free premium users.
  • Subscription model collapse: The entire business model is based on subscription payments. When users figure out they can bypass it, the model falls apart.
  • User data integrity: If subscription status can be modified without payment, what else can be modified without proper authorization? This opens the door to other admin-level operations.
  • Infrastructure abuse: Free premium access likely means more concurrent users, higher bandwidth usage, and increased server load — all eating into infrastructure costs.

Responsible Disclosure

I discovered this vulnerability and reported it through two channels:

  • Email: Sent a detailed report with reproduction steps to the development team.
  • Instagram: Also reached out via their social media account to ensure visibility if the email got missed.

The point of responsible disclosure isn't to embarrass a company — it's to give them time to fix the issue before it becomes public knowledge. I gave them a timeline to patch, and I'm documenting this after a reasonable period to ensure the fix is in place or the issue is public anyway.

Lessons for API Developers

If you're building a subscription system, don't repeat this mistake:

1. Separate test and production environments completely. Test endpoints should live on staging.api.example.com or behind a feature flag that's off in production. Never mix test and production logic.

2. Validate payment status before changing subscription state. Any endpoint that modifies subscription status should verify a transaction against your payment provider. Don't trust the client or a bare API call.

3. Implement role-based authorization. Even if you eventually want certain users to activate their own subscriptions after payment, explicitly check that the user has the right to modify subscription state. Default to "deny."

4. Log and monitor subscription changes. Every subscription activation should be auditable — who changed it, when, and why. If you see patterns like one account activating subscriptions for multiple planIds, that's a red flag.

5. Test your payment flow end-to-end. Make sure the payment → subscription activation flow actually works and requires payment. Don't assume it does.

Closing Thoughts

MalakaBooks is a solid platform for Indonesian readers, but this vulnerability showed that not all code paths were equally scrutinized before production. It happens — especially in growing startups where infrastructure gets built fast and security gets reviewed later. The key is to fix it fast once discovered, which I'm optimistic they will.

If you're running a subscription service, take this as a wake-up call: audit your authorization logic around payment-critical endpoints. Your revenue depends on it.
